# Peer Review — Batch-first game protocols (#22)

## Summary

Six commits land the batch seams the fleet stories will consume:
`BatchPositionProcessor` (concrete, with looping defaults over the
`GamePosition` scalars), `MCTSEngine` and `SelfPlayCollector` routed through it
at width one, `PositionEvaluator` widened to `evaluate_positions`, and
`NeuralNetworkEvaluator` rebuilt around `encode_positions` / `decode_policies`
with a single stacked forward pass. The story, the plan and the code agree on
the shape of the result: every step in the plan is implemented, the sibling
stories (#20, #23, #24) and the README were updated as Step 6 required, and the
test suites gained genuine alignment coverage (index pairing, row-to-position
pairing, batched-equals-elementwise) rather than mechanical renames.

`pyright` reports **0 errors, 0 warnings, 0 informations**; `ruff check .`
reports **All checks passed**; `pytest` is green at **213 passed**.

The findings below are all about the *edges* of the new contracts rather than
their centre: the evaluator seam is undefined on an empty batch and narrower on
value-tensor shape than its docstring claims, and expansion issues one
batch-of-one call per child where the story's own sketch calls for a single
width-B call.
